## Performance Analysis

### Non-CF sites: reqwest vs Chrome

For non-CF sites, flaresolverr-rs averages **~2.4s** via reqwest (direct HTTP), while flaresolverr-py averages **~1.7s** via Chrome. The gap comes from two differences:

| Factor | flaresolverr-rs | flaresolverr-py |
|--------|----------------|----------------|
| HTTP client | reqwest (downloads full body) | Chrome inside Docker/Linux |
| Completion signal | Full response body received | DOMContentLoaded event fired |
| Networking | Windows native TCP stack | Linux kernel TCP stack (Docker) |

Chrome fires at `DOMContentLoaded`, which is significantly earlier than the full body download for chunked or deferred-resource pages. This accounts for the consistent 0.5–1.5s delta.

**Why not use `get_source()` for non-CF sites?**

`chaser-cf::get_source()` navigates Chrome to the URL and then calls `wait_for_clearance(30s)` — polling every 400ms for a `cf_clearance` cookie before returning. On non-CF sites that cookie never appears, so every call blocks for the full 30-second timeout. Using it as a fast path would make non-CF sites ~33s, 14× slower than reqwest. The two-pass reqwest approach remains the correct design.

### CF sites: rs is dramatically faster

For CF-protected sites (🍪 rows), rs averages **~3.1s** vs py's **~11.8s**. rs caches the `cf_clearance` cookie in the chaser-cf browser context and reuses it across requests. py re-solves the Turnstile challenge on every request.
